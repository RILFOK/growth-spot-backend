# Backend — авторизация и роли

## Авторизация
Backend использует JWT Bearer Token.

JWT передаётся в заголовке запроса:

`Authorization: Bearer <token>`

Для защищённых endpoint'ов используется middleware `authenticateToken`.

## Middleware `authenticateToken`
Middleware выполняет:
- проверку наличия токена;
- валидацию JWT;
- загрузку пользователя из базы данных;
- проверку актуальности `tokenVersion`;
- проверку актуальности роли пользователя;
- формирование объекта `req.user`.

Если роль пользователя изменилась или `tokenVersion` больше не совпадает, токен считается недействительным.

Это позволяет принудительно завершать старые сессии, например после смены роли или изменения пароля.

## Роли
В системе используются роли:
- `admin`
- `moderator`
- `manager`
- `viewer`

## Общая модель доступа
Backend использует ролевую модель доступа. Проверка прав выполняется непосредственно внутри endpoint'ов.

В зависимости от роли пользователь может:
- только просматривать данные;
- изменять статусы и содержимое;
- управлять пользователями;
- работать с настройками безопасности;
- изменять конфигурацию сайта.

## Права доступа

### Leads
- просмотр: `admin`, `moderator`, `manager`, `viewer`
- изменение статуса: `admin`, `moderator`, `manager`
- удаление: `admin`, `moderator`

### Users
- просмотр: `admin`, `moderator`, `viewer`
- создание: `admin`, `moderator`
- удаление: `admin`, `moderator`
- смена роли: `admin`
- смена пароля другого пользователя: `admin`, `moderator`

### Blocked IP
- просмотр: `admin`, `moderator`
- разблокировка: `admin`, `moderator`

### IP whitelist
- просмотр: `admin`
- добавление: `admin`
- удаление: `admin`

### IP info
- `GET /api/ip-info` доступен любому авторизованному пользователю

### Settings
- `GET /api/settings/public` — доступен без авторизации, но возвращает только разрешённые публичные ключи из `PUBLIC_SETTINGS_KEYS`;
- `GET /api/settings` — доступен авторизованным пользователям для просмотра настроек;
- `PUT /api/settings` — доступен **только роли `admin`**, проверка выполняется на сервере.

## Завершение двухфакторной авторизации

Временный `tempToken`, полученный после проверки пароля, принимается только endpoint'ом `POST /api/auth/verify-2fa`. Middleware `authenticateToken` отклоняет такие токены для всех обычных защищённых API. Полноценный токен должен содержать роль и числовую версию сессии; её значение и роль сверяются с текущими данными БД.

## Проверки HTTP-маршрутов

Файл `test/http-security.test.js` проверяет настоящие маршруты Express через локальный HTTP-сервер и подмену `pg.Pool.query`. Тестовая база не требуется. Сценарии включают полный вход с TOTP, отказ по временному JWT, устаревшую версию сессии, запрет изменения настроек для viewer и allowlist публичных настроек.

## Ограничение попыток входа

Для развёртывания с одним процессом PM2 подключены независимые IP-based fixed-window ограничения:
- `POST /api/auth/login`: 10 попыток за 15 минут;
- `POST /api/auth/verify-2fa`: 8 попыток за 5 минут;
- `POST /api/auth/disable-2fa`: 6 попыток за 10 минут.

При превышении возвращается `429` и `Retry-After`. Считаются все запросы, включая успешные; счётчики находятся только в памяти процесса и обнуляются при рестарте. При масштабировании на несколько процессов нужен общий Redis-store и дополнительная защита от распределённых атак на стороне reverse proxy/WAF. Вход при ошибочной конфигурации 2FA не должен выдавать полный токен; повторное включение 2FA не перезаписывает уже действующий секрет.
