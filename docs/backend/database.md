# Backend — база данных

## Используемая СУБД
Backend использует PostgreSQL.

Подключение к базе выполняется через `pg.Pool` с использованием переменной окружения `DATABASE_URL`.

## Используемые таблицы
В коде backend используются следующие таблицы:
- `users`
- `leads`
- `settings`
- `blocked_ips`
- `ip_whitelist`

## Известная миграция
В репозитории присутствует только файл `migration.sql`, который создаёт таблицу `settings` и добавляет начальные значения.

Это означает, что полная миграционная история проекта в репозитории отсутствует.

## Таблица `settings`

### Назначение
Таблица `settings` используется как key-value хранилище настроек сайта.

Через неё backend и frontend получают:
- контакты;
- ссылки на мессенджеры и соцсети;
- тексты hero-секции;
- параметры аналитики;
- значения для публичной части сайта.

### Схема

    CREATE TABLE IF NOT EXISTS settings (
      id SERIAL PRIMARY KEY,
      key VARCHAR(255) UNIQUE NOT NULL,
      value TEXT NOT NULL,
      updated_at TIMESTAMP DEFAULT NOW()
    );

### Начальные значения
В `migration.sql` создаются стартовые записи для:
- телефона;
- email;
- Telegram;
- WhatsApp;
- VK;
- графика работы;
- hero-заголовков и описания.

## Таблица `users`

### Назначение
Таблица хранит пользователей административной части сайта.

### Что известно из кода
Backend использует следующие поля:
- `id`
- `email`
- `password`
- `role`
- `name`
- `nickname`
- `two_factor_enabled`
- `totp_secret`
- `token_version`
- `created_at`

### Использование
Таблица участвует в:
- авторизации;
- 2FA;
- проверке роли;
- инвалидировании старых токенов;
- управлении пользователями;
- смене паролей.

## Таблица `leads`

### Назначение
Таблица хранит заявки, отправленные через форму на сайте.

### Что известно из кода
Backend использует следующие поля:
- `id`
- `name`
- `phone`
- `message`
- `status`
- `ip_address`
- `is_spam`
- `spam_reason`
- `created_at`

### Использование
Таблица участвует в:
- сохранении заявок;
- отображении заявок в админке;
- изменении статуса;
- удалении заявок;
- антиспам-логике;
- массовом удалении спам-заявок при разблокировке IP.

## Таблица `blocked_ips`

### Назначение
Таблица хранит IP-адреса, заблокированные антиспам-механизмом.

### Что известно из кода
Backend использует следующие поля:
- `id`
- `ip_address`
- `reason`
- `active`
- `created_at`
- `updated_at`

### Использование
Таблица участвует в:
- блокировке IP при превышении лимита заявок;
- проверке заблокированных IP;
- разблокировке IP;
- хранении причины блокировки.

## Таблица `ip_whitelist`

### Назначение
Таблица хранит IP-адреса, исключённые из антиспам-ограничений.

### Что известно из кода
Backend использует следующие поля:
- `id`
- `ip_address`
- `comment`
- `active`
- `created_at`
- `updated_at`

### Использование
Таблица участвует в:
- исключении IP из лимитов антиспама;
- определении статуса текущего IP администратора;
- ручном управлении whitelist через админку.

## Ограничения текущей документации
На данный момент точная SQL-схема таблиц:
- `users`
- `leads`
- `blocked_ips`
- `ip_whitelist`

не зафиксирована в репозитории и не описана отдельными миграциями.

## Важное замечание
Для полноценного восстановления backend из репозитория не хватает схем таблиц:
- `users`
- `leads`
- `blocked_ips`
- `ip_whitelist`

Рекомендуется:
1. добавить полные SQL-миграции для всех таблиц;
2. либо снять структуру из PostgreSQL и включить её в документацию;
3. либо завести отдельную систему миграций.
